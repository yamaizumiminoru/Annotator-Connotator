# Annotator-Connotator: Connotation機能 会議資料・決定記録

作成日: 2026-08-21
対象: Connotation専用ベンチマークと出力形式の強化
会議相手: LLM

状態: 初回会議実施・初期実装済み。**第15節の会議結果を現時点の決定として扱う。**

## 0. LLMへの依頼

あなたは、語学教育・語用論・LLM評価・アプリ設計の観点を持つプロダクト検討者として、この資料をもとに会議に参加してください。

会議では次の原則を守ってください。

1. **現行実装の事実、既存テストから言えること、新しい提案を区別する。**
2. アプリ名に `Connotator` が含まれることを、専用機能がすでに実装済みである証拠にしない。
3. 「connotation」という語の狭い意味と、学習者向けの「含意・ニュアンス」という広い括りを区別する。
4. 会話含意を、文の論理的・確定的な意味として説明しない。
5. 文脈が足りない場合は断定せず、複数の可能性と確信度を示す。
6. 各論点について、利点、欠点、教育的価値、誤検出リスク、実装負荷を比較する。
7. 一度に全論点を決めず、下記の「会議で決めたいこと」を上から順に一つずつ検討する。
8. 最後に、この資料末尾の「会議結果」フォーマットで合意事項をまとめる。

## 1. この会議の目的

Annotator-Connotatorが、現在どの程度まで語の含みや語用的意味を説明できているかを整理し、次の二点について実装前の仕様案を固める。

1. **Connotation専用ベンチマーク**
   何を「説明できた」とみなすか、どのような例文で、どのように採点するか。
2. **Connotation専用の出力形式**
   通常の語彙・文法annotationと分けるか、何を表示するか、どの程度の不確実性を明示するか。

この会議では実装作業そのものは行わない。まず仕様と評価方法を検討する。

## 2. プロダクトの前提

- どんな文章も、語彙・表現・文法の解説、全文訳、スラッシュリーディングなどを備えた語学教材に変換するアプリである。
- 入力言語、解説言語、画面表示言語として、品質テストを通過した71言語を選択できる。
- アプリ名 **Annotator-Connotator** には、文書を「あの手この手」で教材化することに加え、将来的にはannotationだけでなくconnotationも分かるようにしたい、という意図がある。
- したがって、`Connotator` は現状の完成機能を保証する名称ではなく、プロダクトの方向性も表している。

## 3. 現行実装で確認できること

### 3.1 現在の出力

現行のAPIは、主に次の形式で通常のannotationを返す。

```json
{
  "annotations": [
    {
      "id": "a1",
      "text": "原文中の連続した文字列",
      "type": "vocab|phrase|idiom|grammar",
      "meaningJa": "選択した解説言語による意味",
      "noteJa": "使い方や学習上の注意",
      "example": "用例",
      "start": 0,
      "end": 10
    }
  ]
}
```

`noteJa` に語感・丁寧さ・話者の態度などが書かれることはある。しかし、次のものはまだない。

- connotationを必ず検討するという明示的な指示
- connotation専用の出力欄
- connotationの種類を区別する分類
- 慣習的意味と文脈依存の推論を区別する欄
- 確信度や別解を示す欄
- 「該当なし」を正しく判断するための専用テスト

### 3.2 現在のプロンプトが拾いやすいもの

上級レベルでは、ニュアンスの大きい語彙、イディオム、レジスター、話者のスタンスを優先するよう指示されている。アカデミック設定では、ヘッジやスタンスも優先される。

したがって現状は、**LLMが気づいた語用的情報を通常annotationの `noteJa` に書くことがある**、という状態である。体系的なConnotatorとはまだ言えない。

## 4. 既存テストから言えること・言えないこと

### 4.1 言えること

2026-08-21の言語品質評価では、各言語について情報文と語用的文章を実際の `/api/annotate` に入力し、別のGPT-5.6による採点を行った。

- 元の57言語は、語用的文章を含む2件の入力テストをすべて通過した。
- 評価軸には、イディオム、スタンス、丁寧さ、レジスター、含みの説明が含まれた。
- さらに、同じ英文を各言語で解説する出力言語テストも行った。
- 全体として、明示的なイディオム、丁寧な遠回し表現、スタンス表現を説明できる基礎能力は確認できた。
- ただし、これは母語話者認証ではなく、AIのみを用いたスクリーニングである。

元の57言語の語用的文章だけを見ると、`connotationRegister` の平均は **3.96/4** で、55件が4点、2件が3点、3点未満はなかった。3点だった例は次のとおりである。

- ポーランド語: `może` が提案を和らげる働きを明示的に説明しなかった。
- スワヒリ語: `kuingia mkenge` を「だまされる」に近く説明し、文脈上の「人前で失敗する・格好を悪くする」という含みを十分に捉えなかった。

この結果は、現在のモデルに語用的説明の能力があることを示す一方、**重要な標識の見落とし**と**文脈に合う語感の不足**が実際に起こることも示している。

既存テストの日本語例:

> 委員会は「検討しておきます」と丁寧に答えたが、その言い方には、実際には何もしない可能性が高いという含みがあった。

既存テストの共通英文:

> The committee's reply was technically polite, but the phrase “we will keep it in mind” gently suggested that no action was likely.

### 4.2 言えないこと

上記の例は、文章自体が「何もしない可能性が高いという含み」「no action was likely」と意図を明示している。そのため、主に**明示された語用的意味を適切に説明できるか**を見ており、隠れた含意を自力で発見できることまでは証明していない。

現時点で十分に検証できていないもの:

- 文脈から初めて分かる会話含意
- 皮肉・反語・sarcasm
- 前提や期待とのずれ
- キャンセル可能な推論
- 文化的・社会的連想
- 普通の文に存在しない含意を捏造しない能力
- 複数の解釈がある場合の慎重な説明

### 4.3 暫定評価

| 領域 | 現状の見立て | 主な根拠・限界 |
| --- | --- | --- |
| イディオム | 比較的強い | 既存の語用的文章で評価済み |
| スタンス表現 | 比較的強い | 上級・アカデミック設定でも優先対象 |
| 丁寧さ・婉曲表現 | 中程度以上 | 説明できるが、毎回選択される保証はない |
| レジスター | 中程度以上 | 評価対象だったが専用分類はない |
| 隠れた会話含意 | 未検証 | 既存例は含意を文章内で明示している |
| 前提・期待とのずれ | 未検証 | 専用ケースがない |
| 皮肉・sarcasm | 未検証 | 文脈対照テストがない |
| 文化的連想 | 未検証 | 母語話者評価も未実施 |
| 過剰解釈の抑制 | 未検証 | negative controlがない |

## 5. 用語と機能範囲

### 5.1 狭い意味でのconnotation

語や表現が辞書的意味に加えて慣習的に帯びる、評価的・感情的・社会的な連想。

例:

- `slim` と `skinny`
- 「子供らしい」と「子供っぽい」
- `residence` と `home`

### 5.2 より広い「含意・ニュアンス」

語学学習者が知りたい情報は、狭義のconnotationだけではない。次も教育上は重要である。

- 話者のスタンス
- 丁寧さ・間接性
- 会話含意
- 前提・期待とのずれ
- レジスターと社会的意味
- 皮肉・反語
- 婉曲表現

### 5.3 採用する機能範囲

狭義のconnotationに限定せず、学習者が「この言い方はどう聞こえ、何が推論されうるか」を理解するための**語用情報全般**を扱う。画面上の名称は **「ニュアンス」** とし、内部では種類を区別する。

候補カテゴリ:

```text
evaluative
stance
politeness
implicature
presupposition
register
irony
euphemism
```

トップレベルの8カテゴリは維持する。`politeness` には次の下位分類を持たせる。

```text
positive
negative
mitigation
honorific
other
```

- `positive`: 親しさ、共感、仲間意識、褒め、inclusiveな表現
- `negative`: 距離、配慮、負担軽減、謝罪、遠回しさ
- `mitigation`: 直接性や断定を弱める働き
- `honorific`: 敬語、待遇、上下関係、社会的位置づけ

この下位分類はBrown & Levinsonの枠組みを全言語へそのまま当てはめるためのものではない。多言語比較とUI表示のための運用上のタグとし、各言語の記述では具体的な言語形式と文脈上の働きを優先する。

## 6. Connotation専用ベンチマーク案

### 6.1 最初の規模

最初の専用ベンチマークは、日本語16件、英語16件、計32件とする。

- 8カテゴリ
- 各言語で各カテゴリ2件
- 合計: 8カテゴリ × 2言語 × 2件 = 32件

各カテゴリについて、**次の4パターンを日本語と英語へ分配する**。

1. 明確な検出対象A
2. 明確な検出対象B
3. 文脈によって解釈が変わる例
4. 含意を作ってはいけないnegative control

全32件の中で各パターンが均等になるようにし、どちらか一方の言語だけが常にnegative controlになるような偏りは避ける。`politeness` にはpositive politeness / solidarityの例を必ず含める。

### 6.2 8カテゴリ

| カテゴリ | 見たい能力 | 例 |
| --- | --- | --- |
| 評価的ニュアンス | 辞書的意味を超える肯定・否定評価 | `slim / skinny`、子供らしい／子供っぽい |
| スタンス | 確信、距離、率直さ、留保 | `apparently`、正直なところ |
| 丁寧さ・間接性 | 表面上の形式と対人的効果 | `Could you...?`、検討しておきます |
| 会話含意 | 発話から推論されるが論理的には確定しない意味 | `Some students passed.` |
| 前提・期待 | すでに共有されたものとして扱う情報、意外性 | `Even Ken passed.`、また、ようやく |
| レジスター | 場面、距離、所属集団、社会関係 | `children / kids`、敬語と常体 |
| 皮肉・反語 | 表面の意味と文脈上の評価の反転 | 失敗直後の `Great job.` |
| 婉曲・文化的連想 | 直接表現を避ける効果、慣習的連想 | `passed away`、リストラ |

`politeness` のベンチマークでは、少なくとも次を区別して扱う。

- positive politeness / solidarity: `Come on, you're one of us.` などの仲間意識
- negative politeness / deference: 相手の負担や距離へ配慮する表現
- mitigation: 提案・断定・拒否を和らげる表現
- honorific / social positioning: 敬語、待遇、上下関係を示す形式

### 6.3 二段階評価

#### A. 発見テスト

通常のアプリと同じく、モデル自身が注目箇所を選ぶ。

確認すること:

- 学習上重要な含意を見つけたか
- 適切な範囲を選択したか
- 通常の語彙解説だけで終わらなかったか
- 含意のない箇所を捏造しなかったか

#### B. 説明テスト

対象箇所をあらかじめ指定し、説明の質だけを評価する。

確認すること:

- 表面的意味と含みを区別したか
- 文脈上の働きを説明したか
- 不確実な推論を断定しなかったか
- 学習者に分かる言葉で説明したか

発見テストと説明テストを分けることで、「気づかなかった」のか「気づいたが説明できなかった」のかを区別できる。

### 6.4 採点案

各ケース10点満点:

| 評価項目 | 点数 | 内容 |
| --- | ---: | --- |
| 発見 | 2 | 重要な対象を選べたか |
| 範囲 | 1 | 原文上の範囲が正確か |
| 説明の正確さ | 3 | 含意・ニュアンスを正しく説明したか |
| 文脈への慎重さ | 2 | 文脈依存性、別解、キャンセル可能性を扱えたか |
| 過剰解釈の抑制 | 2 | 根拠のない感情・意図・社会評価を捏造しなかったか |

説明テストでは「発見」2点を除き、8点満点として別集計する方法も考えられる。

### 6.5 重大エラー案

次のいずれかがあれば、合計点にかかわらず不合格とする。

- 皮肉を文字どおりに解釈し、文脈と逆の説明をする
- キャンセル可能な会話含意を、文が論理的に断言した内容として説明する
- 根拠なく敵意、差別、感情、人格、政治的立場などを捏造する
- 通常の辞書的意味だけをconnotationとして提示する
- 文脈不足なのに一つの解釈だけを確定する
- 原文に存在しない語句を対象範囲として返す

### 6.6 採用する初期合格基準

| 案 | 基準 | 特徴 |
| --- | --- | --- |
| 厳格 | 平均8.5/10以上、各カテゴリ平均8以上、重大エラー0、negative control誤検出0 | 公開機能として強く主張しやすいが、初期実装には厳しい |
| 標準 | 平均8/10以上、各カテゴリ平均7以上、重大エラー0、negative control誤検出1件以下 | 品質と開発速度の均衡を取りやすい |
| 段階導入 | 発見と説明を別判定し、説明だけ先に公開。発見はベータ表示 | 失敗原因を切り分けやすいが、UIと説明が複雑になる |

初期ベンチマークには「標準」を採用する。

- 全体平均8/10以上
- 各カテゴリ平均7/10以上
- 重大エラー0件
- negative controlの誤検出1件以下

ただし、平均点よりも **「存在しないニュアンスを作らないこと」** を優先する。敵意、差別、皮肉、拒否などを根拠なく付与する誤検出は、通常の見逃しより重く扱う。重大な誤検出は、上記の「重大エラー0件」によって一件でも不合格とする。

## 7. ベンチマークの具体例

### 7.1 会話含意: キャンセル可能性

**発話A**

> Some students passed the exam.

期待される説明:

- 通常は「全員ではない」可能性をほのめかす。
- ただし `some` の論理的意味は「少なくとも一部」であり、「全員ではない」と断定はできない。

**発話B**

> Some students passed the exam. In fact, all of them did.

期待される説明:

- 後続文によって「全員ではない」という推論が取り消されている。
- 最初の文を矛盾と判定しない。

### 7.2 丁寧さ・間接性: 文脈対照

**文脈A**

> 会議の終わりに、担当者は提案書を閉じながら「検討しておきます」とだけ答えた。

期待される説明:

- 丁寧さを保ちながら、積極的な約束を避けている可能性がある。
- 拒否だと断定はしない。

**文脈B**

> 担当者は「検討しておきます。金曜日までに費用を比較して回答します」と答えた。

期待される説明:

- 後続する具体的な行動予定により、単なる婉曲な拒否とは読みづらい。

### 7.3 皮肉: 文脈による反転

**文脈A**

> You fixed every error before the deadline. Great job.

期待される説明: 通常の肯定的評価。

**文脈B**

> You deleted the final file five minutes before the deadline. Great job.

期待される説明: 文脈上は皮肉であり、実際には非難を表す可能性が高い。

### 7.4 Negative control

> 図書館は午後九時に閉館します。

期待される結果:

- 通常は、隠れた敵意、皮肉、拒否、価値判断などを付け加えない。
- 必要であれば語彙・文法annotationはしてよいが、Connotation出力を無理に作らない。

### 7.5 Positive politenessと境界例

**Solidarity**

> Come on, you're one of us.

期待される説明:

- `one of us` が仲間意識と心理的距離の近さを作る。
- 文脈によっては励ましにも、同調圧力にもなりうるため、前後関係なしに一方へ断定しない。

**称賛と皮肉の境界**

> さすが田中さんですね。

期待される説明:

- 通常は期待どおりの能力や実績への称賛になりうる。
- 失敗直後、過剰なイントネーション、対立的な会話などの文脈では皮肉になりうる。
- 文字列だけから皮肉と決めつけない。

## 8. 専用出力形式案

### 8.1 決定: `connotations` を独立させる

```json
{
  "connotations": [
    {
      "id": "c1",
      "text": "検討しておきます",
      "start": 5,
      "end": 14,
      "scope": "utterance",
      "category": "politeness",
      "secondaryCategories": ["implicature"],
      "subtype": "mitigation",
      "literalMeaning": "後で検討する",
      "suggestedMeaning": "積極的に対応する約束を避けている可能性がある",
      "pragmaticEffect": "表面的な丁寧さを保ちながら、相手の期待を弱める",
      "contextNote": "本当に検討する場合もあり、文脈なしには拒否と断定できない",
      "confidence": "medium",
      "alternatives": [
        "具体的な検討予定が後続する場合は、文字どおりの約束になりうる"
      ],
      "evidence": [
        "具体的な期限や次の行動が示されていない"
      ],
      "conventionality": "mixed"
    }
  ]
}
```

### 8.2 独立させる理由

- 通常annotationとConnotationは、同じ文字列を重複して扱うことがある。
- 現行annotationsには「重複範囲を避ける」という制約があり、同じ箇所を語彙と含意の両方で説明しにくい。
- 通常の意味説明と、文脈依存で不確実な推論では、必要な欄と注意事項が異なる。
- 専用配列なら、Connotationだけを表示・非表示にしやすい。
- 将来、ベンチマーク結果をカテゴリ別に集計しやすい。

### 8.3 比較対象

| 方式 | 長所 | 短所 |
| --- | --- | --- |
| 既存annotationsに統合 | 実装変更が小さい | 通常の意味と推論が混ざる。重複範囲の問題がある |
| `connotations` を独立 | 概念と評価が明確。専用UIを作りやすい | API・画面・エクスポートの変更が必要 |
| 通常annotationの子要素にする | 同じ語句の説明をまとめられる | 文全体や発話関係にまたがる含意を表しにくい |

### 8.4 内部APIの必須項目

内部APIでは、各Connotation項目について次をすべて生成する。配列項目は該当がなければ空配列にできるが、プロパティ自体は省略しない。

- `text`, `start`, `end`: 根拠となる原文の連続範囲
- `scope`: `span|sentence|utterance|passage`
- `category`: 中心となる主カテゴリ。8種類のトップレベルカテゴリから一つ
- `secondaryCategories`: 教育上必要な場合だけ付ける副カテゴリの配列。主カテゴリは重複させない
- `subtype`: 下位分類。適切なものがなければ `unspecified`
- `literalMeaning`: 表面的・辞書的な意味
- `suggestedMeaning`: 通常推論される意味
- `pragmaticEffect`: 対人関係や談話上の働き
- `contextNote`: 成立条件、別解、断定できない理由
- `confidence`: `high|medium|low`
- `alternatives`: 複数の可能な解釈の配列
- `evidence`: 解釈を支える原文・文脈上の手がかりの配列
- `conventionality`: `conventional|contextual|mixed`

通常annotationとConnotationの対象範囲は重複してよい。Connotation同士の重複は、異なる分析が教育上必要な場合に限る。

### 8.5 APIとUIを分ける

内部APIは検証と再利用に必要な情報を常に保持する。画面では同じデータから表示量だけを変える。

| 表示量 | 画面に出す内容 |
| --- | --- |
| 少なめ | 学習者向けの短いニュアンス説明 |
| 標準 | 表面的な意味、含み、理由・文脈 |
| 詳しく | 別解、確信度、根拠、慣習的か文脈依存かを追加 |

このスライダーは分析結果の情報を捨てるものではなく、表示の詳しさを調整する。既存の抽出量スライダーと考え方をそろえる。

## 9. 画面案

### 9.1 決定した基本方針

- 画面上の機能名: **ニュアンス**
- 語や表現に結びつくものは、通常annotationと同じカード内に表示
- 文全体・発話全体にまたがるものは、文または発話範囲のカードとして表示
- 表示量は「少なめ・標準・詳しく」のスライダーで変更
- 該当するものがない場合は無理に表示しない
- 確信度は「詳しく」で表示する

カードの表示候補:

```text
意味
例文
使い方
ニュアンス

標準・詳しくでは必要に応じて:
表面的な意味
推論されうる意味
文脈上の働き
注意・別の読み方
確信度
```

語彙カードへ収めるために含意の対象範囲を不自然に縮めてはならない。`scope` が `sentence|utterance|passage` の場合は、該当範囲全体を根拠として独立したカードを作る。

### 9.2 常時実行か、任意実行か

| 方式 | 長所 | 短所 |
| --- | --- | --- |
| 常時実行 | 操作が増えず、見落としにくい | 出力増加、費用増加、誤検出が常に見える |
| 切り替え式 | 必要なときだけ使える。試験的導入に向く | 学習者が機能に気づかない可能性がある |
| 高度設定に連動 | 上級教材では自然に有効化できる | 初級文にも重要な丁寧さがあるため単純連動は難しい |

表示量スライダーを設けることは決定した。一方、ニュアンス分析そのものを常時実行するか、別の有効化スイッチを設けるかは、API費用・応答時間を測って実装前に確定する。

## 10. プロンプトの中心要件案

```text
学習者に役立つ、原文と文脈に根拠のある含意・ニュアンスだけを抽出する。
すべての文章に含意があるとは仮定しない。
辞書的意味、慣習的なニュアンス、その文脈だけで生じる推論を区別する。
会話含意を、文が論理的に確定した意味として説明しない。
文脈が不足している場合は、複数の可能性または不確実性を示す。
皮肉・敵意・差別・感情・人物像を、根拠なく付け加えない。
```

追加で検討する指示:

- 学習者のレベルに応じて説明の用語を変えるか
- 解説言語ごとに語用論用語をローカライズするか
- 文化的連想について、地域・世代差を明記させるか
- 1文だけでは判断できない場合、前後の文脈を要求するか

## 11. AIだけでどこまで評価できるか

### 11.1 AIだけでもできること

- 仕様どおりのJSONか
- 対象範囲が原文と一致するか
- 既知の最小対やキャンセル例で論理的な誤りがないか
- 同じ入力に対して大きく不安定でないか
- 一つのモデルが生成し、別のモデルが採点する一次スクリーニング
- negative controlで過剰解釈しないか

### 11.2 AIだけでは保証しにくいこと

- 母語話者にとっての自然さの最終保証
- 地域、世代、共同体ごとの細かな語感
- 差別語・侮蔑語・政治的含意の現在性
- 文化的連想の代表性
- 教室で本当に理解しやすい説明か

したがって、最初はAIのみで再現可能なベンチマークを作り、**「母語話者認証済み」とは表示しない**。将来利用者から具体的なフィードバックを得た場合に、ケースと正解基準を更新する。

## 13. プロダクト設計上の位置づけ

### 13.1 AnnotatorとConnotatorの分業

> **Annotatorは「何を意味するか」を教える。**
> **Connotatorは「その言い方を選ぶと、どう聞こえ、何が推論されうるか」を教える。**

たとえば辞書的意味だけなら `skinny` を理解できても、なぜその文脈で `slim` ではなく `skinny` が選ばれたのかは十分に分からない。Connotatorは、この選択が生む評価、距離、話者の態度、推論可能な意味を扱う。

### 13.2 教材化pipeline

今後の機能は別々の追加機能ではなく、一つの教材化pipelineとして整理する。

```text
Input   : 文章 / YouTube / 音声
  ↓
Analyze : annotation / connotation / CEFR
  ↓
Learn   : カード / 単語帳 / 読解
  ↓
Export
```

YouTube文字起こし、単語帳、CEFR難易度判定、Connotatorは並行トラックで進められる。共通の入力・分析・学習・書き出しという境界を意識し、各機能が孤立したデータ形式を作らないようにする。

### 13.3 多言語検証

日本語と英語の32件で再現可能なコアベンチマークを作りつつ、仕様の英語偏重を早期に見つけるため、次のsentinel languagesを併用する。

- 日本語
- 英語
- 中国語
- 韓国語
- スペイン語
- トルコ語
- アラビア語

sentinel languagesでは、敬語、T/V区別、談話粒子、語順、婉曲表現、社会的距離など、言語間で異なる現象を重点的に確認する。仕様が安定した後、71言語では各言語の代表例を用いたsmoke testを行う。71言語すべてについて毎回32件相当のフルベンチマークを行う必要はない。

## 15. 会議結果

### 15.1 決定事項

1. **機能範囲**
   狭義のconnotationに限定せず、丁寧さ、距離、スタンス、会話含意、前提、レジスター、皮肉、婉曲表現などの語用情報全般を扱う。

2. **カテゴリ**
   トップレベルの8カテゴリを維持する。中心的な働きを `category`、重なる働きを `secondaryCategories` に記録する。`politeness` の下に `positive|negative|mitigation|honorific|other` の `subtype` を持たせる。これは全言語へ単一理論を押しつける分類ではなく、運用上のタグとする。

3. **出力構造**
   通常annotationから独立した `connotations` 配列を設ける。`scope` により語句、文、発話、文章全体を扱えるようにする。通常annotationとの範囲重複を認める。

4. **不確実性の表現**
   内部APIでは `literalMeaning`、`suggestedMeaning`、`pragmaticEffect`、`contextNote`、`confidence`、`alternatives`、`evidence`、`conventionality` をすべて保持する。

5. **UI名称・配置**
   画面名は「ニュアンス」。語句に結びつく説明は通常annotationと同じカードへ表示する。文・発話全体にまたがる説明には独立した範囲カードを使う。本文タブでは対象範囲を赤い下線で示し、クリックして詳細を開ける。表示量は「少なめ・標準・詳しく」のスライダーで変える。

6. **ベンチマーク構成**
   最初は日本語16件＋英語16件の計32件。明確な検出例、文脈依存例、cancellation / contrast、negative controlを全体へ均等に入れる。`politeness` にはpositive politeness / solidarityを必ず含める。

7. **合格基準**
   全体平均8/10以上、カテゴリ平均7/10以上、重大エラー0、negative control誤検出1件以下。平均点より「ないニュアンスを作らない」ことを重視する。

8. **公開時の表現**
   機能実装後は「語や表現のニュアンス・含意も説明」「Connotation-aware language annotation」と表現してよい。一方、「71言語で高精度に検出」「文化的含意を正確に理解」などの品質保証は、対応するベンチマーク通過後まで使わない。

9. **多言語展開**
   日本語・英語だけで仕様を閉じず、中国語、韓国語、スペイン語、トルコ語、アラビア語を加えたsentinel languagesで早期検証する。その後71言語のsmoke testへ広げる。

10. **ロードマップ上の位置**
    Connotator、YouTube文字起こし、単語帳、CEFRを並行トラックとして扱い、Input → Analyze → Learn → Exportの教材化pipelineへ統合する。

### 15.2 保留事項

- ニュアンス分析を常時実行するか、別の有効化スイッチを設けるか
- 表示量スライダーと既存の抽出量スライダーを一つにするか、別々にするか
- `subtype` をカテゴリ共通の自由値にするか、カテゴリごとの列挙型にするか
- 32件の各ケース本文、期待値、許容される別解
- sentinel languagesのテスト件数と、71言語smoke testの合格条件
- 地域差・世代差・文化的連想をどの形式で注記するか

### 15.3 採用しなかった案

- **狭義のconnotationだけを扱う**: 学習者が必要とする丁寧さ、距離、含意、皮肉などが落ちるため。
- **通常annotationsだけで表現する**: 意味と語用推論が混ざり、対象範囲の重複や文全体の分析を扱いにくいため。
- **Connotation専用タブだけに分離する**: 語彙学習時に意味とニュアンスを一緒に見られる利点を失うため。ただし文・発話範囲には独立カードを用いる。
- **日本語・英語だけで完成後に多言語化する**: 英語中心の語用論分類を固定してしまう危険があるため。
- **71言語すべてで毎回フルベンチマークする**: 費用と時間が大きく、仕様検証にはsentinel languages＋smoke testの方が適するため。

### 15.4 次の作業

1. 32件の日本語・英語ベンチマークケースを作成する。
2. ケースごとに正解必須要素、許容される別解、禁止する過剰解釈を定義する。
3. `connotations` のJSON Schemaを確定する。
4. 発見テストと説明テストの評価スクリプト仕様を作る。
5. sentinel languages向けの小規模ケースを選ぶ。
6. UIの少なめ・標準・詳しく、および文・発話範囲カードを画面案にする。
7. API費用と応答時間を測り、常時実行か有効化スイッチかを決める。

### 15.5 実装時の中心原則

> **Annotatorは「何を意味するか」を教える。**
> **Connotatorは「その言い方を選ぶと、どう聞こえ、何が推論されうるか」を教える。**

辞書的意味と語用的推論を混同せず、推論の根拠と不確実性を学習者へ伝える。とりわけ、存在しない敵意・皮肉・拒否・差別性などを作らないことを優先する。

## 16. 初期実装状況

2026-08-21に次を実装した。

- `server.js`: 独立した `connotations` 出力、全必須項目、対象範囲の正規化、過剰解釈を抑えるプロンプト
- `script.js`: 語句カードへの統合、本文中のニュアンス範囲表示、主・副カテゴリ、3段階の表示量、JSON・Markdown出力
- `index.html` / `styles.css` / `languages.js`: ニュアンス操作、件数、表示ラベル、レスポンシブ表示
- `tests/connotation-benchmark-cases.json`: 日本語16件＋英語16件の固定ケース
- `scripts/evaluate_connotations.mjs`: 発見テスト・説明テスト、構造検査、AI採点、合否集計
- `POST /api/youtube-transcript`: 公開字幕の取得、タイムスタンプ除去、任意のLLM補正、入力欄への受け渡し

実APIの短い確認では、失敗直後の `Great job.` と「さすが田中さんですね」を高確信度の皮肉として説明した。前者は専用評価スクリプトの発見テスト＋AI採点でも10/10だった。`Some students passed ... all of them did` の説明テストでは、「not all」は論理的含意ではなく、後続文でキャンセルされる推論だと正しく区別し、構造検査にも合格した。

初回は中立文の `is stored` を過剰にimplicatureとして扱ったため、通常の語義・語彙的含意・日常的連想をConnotationへ昇格させない規則を追加した。再確認した `The cable is two meters long.` では `connotations: []` になった。

固定32件の構造検査は通過済み。全ケースの実API＋AI採点はまだ実行していないため、多言語での高精度を保証する表現は引き続き使用しない。
